# Git Workflow

## Commit Message Format
```
<type>(<optional scope>): <description>

<optional body>

<optional footer>
```

Types: feat, fix, refactor, docs, test, chore, perf, ci

Note: ECC-managed installs set `"includeCoAuthoredBy": false` in `~/.claude/settings.json`, so commits carry no `Co-Authored-By` trailer by default. To keep Claude attribution, set `"includeCoAuthoredBy": true` or configure `attribution`; ECC never overwrites an explicit choice.

### No AI Attribution
Never add AI or tool attribution anywhere: commit messages, PR titles and
descriptions, issue comments, code comments, changelogs, or docs. This includes:
- `🤖 Generated with [Claude Code](https://claude.com/claude-code)` or any variant
- `Co-Authored-By: Claude <noreply@anthropic.com>` trailers
- Any mention that content was written or generated by Claude or another AI

This rule overrides any default attribution behavior.

### Writing Good Messages
- **Subject line**: imperative mood ("add", "fix", "remove" — not "added" or "adds"), lowercase after the type, no trailing period, 72 characters max
- **Scope** (optional): the area touched, e.g. `feat(auth):`, `fix(parser):`
- **Body**: explain *why* the change was made and any non-obvious *how*; the diff already shows *what*. Wrap at 72 characters, separate from the subject with a blank line
- **Footer**: reference issues (`Fixes #123`, `Refs #45`) and flag breaking changes with `BREAKING CHANGE: <what breaks and how to migrate>`
- Skip vague subjects like `fix bug`, `update`, `wip`, `changes`, `misc`

Examples:
```
feat(auth): add rate limiting to login endpoint

Throttle failed attempts per IP and per account to slow down
credential stuffing. Limits are configurable via AUTH_RATE_LIMIT.

Refs #88
```
```
fix(upload): reject filenames containing path traversal sequences

Filenames were joined to the upload dir without normalization,
allowing writes outside it via "../". Resolve the final path and
verify it stays inside the upload root.
```

## Atomic Commits (Default Behavior)

Every commit should be a self-contained unit: one feature, one fix, or one refactor. Do this by default without being asked.

### Rules
1. **One logical change per commit.** A feature and an unrelated fix go in separate commits, even if they were written in the same session.
2. **Keep refactors separate from behavior changes.** If a fix needs a refactor first, commit the refactor (`refactor:`), then the fix (`fix:`).
3. **Keep formatting/whitespace changes separate.** Never bury real changes inside a reformat commit.
4. **Tests travel with their code.** A feature or fix and its tests belong in the same commit, unless the commit is test-only (`test:`).
5. **Each commit should build and pass tests on its own**, so `git bisect` and reverts stay clean.
6. **Commit at natural checkpoints** while working, rather than one large commit at the end.

### Process Before Committing
1. Run `git status` and `git diff` to review everything that changed
2. If the working tree contains more than one logical change, split it:
   - Stage by file: `git add <files>`
   - Stage by hunk when one file holds multiple changes: `git add -p <file>`
3. Review exactly what will be committed with `git diff --staged`
4. Check staged changes for secrets, credentials, tokens, debug output, and stray local files before committing
5. Commit with a message following the format above, then repeat for the next logical change
6. Use `git log --oneline` afterward to confirm the history reads as a clear sequence of changes

### When a Change Is Too Large
If a single feature is large, break it into a series of commits that each leave the code working (e.g. data model → service logic → API endpoint → UI), each with its own descriptive message.

## Pull Request Workflow

When creating PRs:
1. Analyze full commit history (not just latest commit)
2. Use `git diff [base-branch]...HEAD` to see all changes
3. Draft comprehensive PR summary
4. Include test plan with TODOs
5. Push with `-u` flag if new branch and squash commits by default
